# CR-036 — Measurement configuration & verification: GA4 property configuration, verification protocol, Consent Mode v2, default event taxonomy, measurement health checks

**Number note (2026-10-14):** drafted as CR-035; renumbered to CR-036 because CR-035 is taken by `wef-cr-035-intake-web-form` (Intake web form). Re-check the next-free number immediately before merge.

## Problem

The framework requires analytics to **exist and fire**, but not to be **configured, verified
correctly, or kept healthy**:

1. **GA4 property configuration is unspecified (G-1).** SG10.5 Sec. 11 checks that "GA4, Search
   Console, GTM, and Clarity all verified firing correctly on staging". Nothing requires key events
   to be marked, event data retention to be raised from the 2-month default, Search Console to be
   linked to GA4, internal/developer traffic to be filtered, payment/booking/CRM domains to be
   listed as unwanted referrals, Enhanced Measurement to be reconciled against custom events, or a
   reporting identity to be chosen. Several of these are not retroactive, so every week of delay is
   lost history.
2. **"Verified firing" has no method (G-5).** SG11 Sec. 11 asks for events "tested in
   debug/realtime reporting", but most WordPress analytics integrations exclude logged-in users, so
   an operator testing while signed in to WordPress sees nothing, or sees a different tag set from
   the one visitors get.
3. **Consent Mode is not specified (G-6).** WPConsent is a standing layer (Governance Sec. 13.4)
   and consent-gating is a QA line (RETRO-008), but Google Consent Mode v2 (`ad_storage`,
   `analytics_storage`, `ad_user_data`, `ad_personalization`) is never mentioned. Without it,
   consent-denied visits are dropped rather than modeled, and Google Ads features are limited for
   regulated-region traffic.
4. **No default event taxonomy (G-7).** The Meaningful-Action Measurement Plan (Reusable Templates
   Sec. 7.4, part 3) is a blank table by design, so each engagement invents event names. That
   blocks cross-engagement comparison and makes CR-037's CRM attribution mapping
   engagement-specific.
5. **No standing measurement-health check (G-13).** The weekly cadence (Sec. 7.4, part 6) lists
   "conversion-event health" with no test behind it. Launch monitoring (SG11 Sec. 11) covers only
   the first 24/72 hours. Low-traffic sites have no Chrome UX Report (CrUX) field data, so lab
   results get reported as if they were field data.

## Evidence (originating engagement, client detail minimized)

A real-estate engagement reviewed on 2026-10-05:

- **Key event marked late.** `generate_lead` fired correctly from launch, but was marked as a key
  event weeks after the forms went live. Key-event reporting does not backfill, so the early leads
  never appear as key events.
- **Search Console not linked to GA4.** The WordPress analytics plugin was connected to both
  products, which looked like an integration, but the GA4 → Search Console product link had never
  been made. GA4 had no organic-query reports, and its own recommendations panel was flagging the
  missing link.
- **Logged-in tests were invisible, and a second tag appeared.** Both labelled test submissions ran
  while the operator was logged in to WordPress, so neither reached GA4. A second, unexplained GA
  measurement ID loaded **only for logged-in administrators**. That violates Governance Sec.
  13.4.4's single analytics/tag path, and only a tag inventory taken in both states catches it.
- **Internal-traffic filter needed an operator decision.** Defining internal traffic is reversible.
  Switching a GA4 data filter from *Testing* to *Active* permanently excludes matching data, and
  the UI warns about this. The agent stopped and asked the operator, as Governance Sec. 13.4.5's
  last bullet requires for irreversible production work. The checklist should expect that pause.
- **Silent CRM failure.** The form → CRM bridge returned success while the CRM API silently
  dropped the tag and pipeline-stage fields. Only a manual look at the CRM record caught it. A
  weekly synthetic lead read back from the CRM would have caught it within a week.
- **A good taxonomy emerged locally.** The engagement's own measurement plan defined
  `generate_lead`, `contact` (tel:/mailto:), `select_content`, `tool_start`/`tool_complete` and
  standard parameters `lead_type`, `form_id`, `page_type`, `service_interest`, `cta_location`, plus
  a `dataLayer` contract. Only two events were actually implemented. The framework needs both a
  default taxonomy and a checklist line that compares the plan with what was built.

### Insert A — SG10.5 Sec. 11 "GA4 Property Configuration" checklist block

```markdown
- [ ] **GA4 Property Configuration (CR-036)** — verified in GA4 Admin on the production property,
      recorded in the Plugin & Integration Configuration Record (Reusable Templates Sec. 15.2):
  - [ ] **Key events** marked for every primary meaningful action in the measurement plan
        (at minimum `generate_lead`) before the first production form goes live. Key-event
        marking does not backfill.
  - [ ] **Event data retention** set to 14 months (the standard-property maximum) instead of the
        2-month default. Not retroactive; set it on day one.
  - [ ] **Search Console linked to GA4** (Admin → Product links) with the correct web data stream,
        and the Search Console report collection published in the GA4 Library. A plugin connected
        to both products does not count as this link.
  - [ ] **Internal traffic** defined (operator/client office IPs) and the internal-traffic and
        developer-traffic data filters created in *Testing* state. Moving a filter to *Active*
        permanently excludes matching data, so it requires the operator's explicit approval,
        logged as a Decision Register entry (Governance Sec. 13.4.5).
  - [ ] **Unwanted referrals** list includes every payment, booking, scheduling, CRM and identity
        domain a visitor round-trips through.
  - [ ] **Enhanced Measurement** reconciled against custom events: form interactions, file
        downloads and outbound clicks are either off or documented as non-key, so no meaningful
        action is counted twice.
  - [ ] **Reporting identity** chosen (Blended / Observed / Device-based) and the reason recorded.
  - [ ] **Correct property per site**: the measurement ID in rendered output matches this client's
        property (Governance Sec. 13.4.4, client/account isolation).
```

### Insert B — Prompt 10.5.5 (copy-paste, any engagement)

```
Configure and verify Google Analytics 4 for [Client Name]'s site
[https://domain.com], GA4 property "[property name]" (I will confirm the
property in the GA4 UI; do not infer it). Follow Governance Sec. 13.4.4
(one writer; rendered output is the truth) and Sec. 13.4.5 (credentials,
irreversible actions).

Ground rules:
- I (the site owner, or my delegate) sign in. You never create accounts,
  enter passwords, or type API secrets or keys. If a value is needed, tell
  me exactly where to paste it and verify without printing it.
- Before any action GA4 marks as permanent (activating a data filter,
  lowering retention, deleting a stream or data), stop and ask me. Log my
  answer in the Decision Register.
- Send no personal data (name, email, phone, address, free-text) in any
  event name, parameter or URL.

Steps:
1. Inventory: list every GA4 measurement ID, GTM container and ad pixel in
   the rendered HTML/network requests twice: once logged out (private
   window) and once logged in to WordPress. Report any ID present in only
   one state and who emits it. There must be exactly one analytics path.
2. Key events: mark every primary event in the measurement plan as a key
   event (at minimum generate_lead). List what is marked.
3. Retention: set event data retention to 14 months.
4. Search Console: create the GA4 -> Search Console product link for the
   web stream, then publish the Search Console report collection.
5. Internal traffic: define internal traffic rules for the IPs I give you.
   Create the internal and developer traffic filters in Testing state only.
   Ask me before switching either to Active.
6. Unwanted referrals: add every payment, booking, CRM and identity domain
   in the Integration Requirements Spec.
7. Enhanced Measurement: compare its toggles to the custom events and turn
   off, or document as non-key, anything that double-counts a meaningful
   action.
8. Reporting identity: report the current setting and recommend one, with a
   one-line reason. Change it only on my OK.
9. Consent Mode v2: in Tag Assistant, show the default consent state before
   any choice and the update after Accept and after Decline, for
   ad_storage, analytics_storage, ad_user_data, ad_personalization. Confirm
   no analytics cookie is set before consent (RETRO-008).
10. Verification: in a logged-out private window, complete one labelled
    test submission per primary form ("TEST - [date] - [form]"). Show each
    event in DebugView or Realtime with its parameters, then confirm the
    test record in the destination system.
11. Record everything in the Plugin & Integration Configuration Record and
    the measurement plan's Debug Test column (date, method, result).
Report each step as done, blocked, or awaiting my approval, with evidence
(screenshot, count or setting value). Never claim "verified" from a
logged-in session.
```

### Insert D — Reusable Templates Sec. 7.4 part 3 "Default Event Taxonomy"

```markdown
**Default Event Taxonomy (CR-036).** Start every measurement plan from these names. They are GA4
recommended events where one exists. Rename only with a recorded reason; add vertical events
through the active Industry Module.

| Event | Fires when | Key event? | Required parameters (no PII) |
|---|---|---|---|
| `generate_lead` | A lead form, booking or quote request completes successfully (success state, not the submit click) | Yes | `lead_type` (form/booking/quote/callback), `form_id`, `page_type`, `cta_location` |
| `contact` | A tel:, mailto:, SMS or chat-launch link is activated | Per Module (CR-038) | `method` (phone/email/sms/chat), `cta_location`, `page_type` |
| `select_content` | A visitor chooses a listing, service, location card or other content item | No | `content_type`, `item_id`, `cta_location` |
| `tool_start` / `tool_complete` | A calculator, quiz or estimator is first used / produces a result | `tool_complete` optional | `tool_name`, `page_type` |
| `file_download` | A governed asset (guide, checklist) is downloaded | No | `file_name`, `content_type` |
| `qualify_lead` / `close_convert_lead` | Server-side only, sent from the CRM (CR-037) | Optional | `lead_type`, `lead_source` |

**Standard parameters:** `lead_type`, `form_id`, `page_type`, `service_interest`, `cta_location`,
`method`. Values are lower_snake_case, drawn from a fixed list recorded in the plan.

**dataLayer contract.** Site code pushes `{event: '<name>', ...params}` to `window.dataLayer`, and
GTM (or the single tag owner) maps it to GA4. Form, booking and chat vendors connect through a small
adapter that listens for the vendor's success callback and pushes the neutral event. A
vendor-native GA4 integration never runs alongside it (Governance Sec. 13.4.4).
```

## Why core, and why "required" rather than "highly recommended"

Unlike CR-034's layers, none of this needs the client to open a new account. Each step configures
a property the default stack already provisions (Governance Sec. 13.4). Several settings are not
retroactive, so SG10.5 is the only cheap time to set them. The one client/operator touchpoint is
the irreversible filter activation. The checklist routes it through an explicit approval rather
than blocking exit: if approval is deferred, that is recorded and the filter stays in *Testing*.

## Not changed

- **No Industry Module changes.** Vertical events (for example listing searches or appointment
  types) are added through each Module's existing Content Model and Stage Gate Injection Map at the
  Module's next revision.
- **RETRO-008's consent-gating test is unchanged.** Consent Mode v2 is added alongside it, not in
  place of it.
- **No new default-stack layer.** GA4, GTM, Search Console and WPConsent are already in Governance
  Sec. 13.4. Dashboard tooling is in CR-037's scope; channel segmentation is in CR-038's.
- **No RETRO filed.** The late key event and the logged-in-only tag are candidates for
  RETRO-022/023. See open questions.

## Open questions for the Governance Board

1. **Required or highly recommended:** should the GA4 Property Configuration block be an SG10.5
   exit requirement (as drafted), or "highly recommended" like CR-034?
2. **Reporting identity default:** should WEF set one default (for example Blended), or only
   require the choice to be recorded?
3. **Consent Mode basic vs. advanced:** advanced mode sends cookieless pings before consent so
   Google can model denied visits. Should WEF default to basic (more conservative), or to advanced
   where the Charter's Regulatory/Compliance Framework allows it?
4. **Taxonomy strictness:** is the default taxonomy a *starting point* (as drafted), or a
   *controlled vocabulary* that needs a CR to extend?
5. **RETROs:** should the late key-event marking and the logged-in-only second GA ID be filed as
   RETRO-022/023 in Governance Sec. 15.4 under this CR?
